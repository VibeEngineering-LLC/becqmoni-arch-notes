Волна 0: дефекты, дающие неверные числа сегодня

Реестр для передачи автору BecqMoni. База: ветка roi-wizard-reworked, коммит d80c7ee (при переносе на master номера строк потребуют пересчёта). Каждый пункт проверен прямым чтением кода или поставочных конфигов; ни один не требует смены модели данных.

Порядок — по тяжести последствий для пользователя. Атрибуция находки указана явно при каждом пункте: часть механизмов уже описана самим автором BecqMoni в его рабочем документе по рефакторингу (arch/architecture-refactor.md) — здесь они не переоткрыты, а собраны в один список вместе с проверенными нами дефектами; один пункт — в коде нашего собственного инструмента (RoiWizard), не апстрима.

A. Продукт не работает из коробки

A1. Библиотечный фит не стартует никогда на свежей установке. Поставочный config/NuclideDefinition.xml — 77 записей, ноль тегов Sets, ноль IsAnchor, ноль Intencity. Гейт LibraryPeakFitter.cs:480 фильтрует линии по членству в наборе, :483-485 требует хотя бы один якорь — при пустых Sets фит выходит сразу. Оговорка: миграция существующих установок требует FormatVersion в NuclideDefinitionFile (пункт 1 arch-документа), поставочный config/ копируется только при отсутствии каталога (MainForm.cs:102-103).

A2. Активность считается по чужой кривой эффективности — по умолчанию, у всех. EfficencyROIGuid не проставлен ни в одном из 9 файлов config/device/*.xml. DocEnergySpectrum.cs:451-457: при отсутствии Guid берётся ROIConfigList[0], :459 записывает этот Guid в документ. Список отсортирован по LastUpdated (ROIConfigData.cs:213), то есть [0] — произвольный конфиг; на свежей установке это Obsidian Marinelli 0.5.xml — файл с дефектом A3. Запись Guid в документ делает подмену необратимой. Атрибуция: сам механизм (fallback на ROIConfigList[0], защита через BoundEfficiencyConfig) описан автором в arch-документе; здесь — независимая проверка кода и связь с конкретным поставочным файлом A3.

A3. Узел кривой с физически невозможной эффективностью. config/ROI/Obsidian Marinelli 0.5.xml:59-61: Energy=20, Efficiency=1471.85, ErrorPercent=554 при остальных 149 точках в диапазоне 2,8·10⁻⁵…5,6·10⁻³. ε > 1 невозможна; монотонный сплайн утаскивает левый край кривой.

B. Молчаливые нули и подмены

B4. Области, созданные мастером, дают нулевую активность. RoiWizard/SetExporter.cs:51-60 заполняет Name/Enabled/PeakEnergy/границы/Color/HalfLife/Intencity, но не BecquerelCoefficient. Расчёт MeasurementResultManager.cs:48 умножает на 0. Атрибуция: дефект в коде нашего собственного инструмента (RoiWizard-конструктор), не апстрима BecqMoni.

B5. Тихий нуль K неотличим от «не посчитано». ROIConfigForm.cs:951 требует HasEfficiency && Intencity > 0, :955 — effData != null && Efficiency > 0; при провале любого условия K остаётся дефолтным 0 без статуса. Живой репродьюсер в поставке: config/ROI/Ra-226 Intensities.xml — 16 областей с заполненными интенсивностями и K=0 (то же в Th-232 Intensities.xml — 11 областей); первый файл — находка внешнего ревью, второй найден нами при проверке того же паттерна по остальным поставочным файлам. Сюда же ветка Utils/ROIAriphmetics.cs:28-31: запрос ε вне [MinEnergy, MaxEnergy] возвращает null, вызывающий код молча пропускает расчёт.

B6. Ссылка между областями резолвится по имени — риск, не действующий дефект сегодня. MeasurementResultManager.cs:372-386: первая область с совпавшим именем, break. При дубле имён вторая недостижима, а при отсутствии совпадения цикл проходит вхолостую и netCounts остаются нулями без сообщения. Механизм подтверждён кодом. В поставке дубли имён есть (две области «Co60» в Cs134,Cs137,K40.xml, одиннадцать «Ra-226» в Ra226 + K40.xml), но ни одна <Reference> в проверенных 12 файлах на дублированное имя не ссылается — сегодня дефект не наступает, это риск на будущее при редактировании конфигов.

B7. Одиннадцать областей с одинаковым коэффициентом. config/ROI/Ra226 + K40.xml: 11 из 12 областей несут BecquerelCoefficient=290. Разные линии Ra-226 с разными ε и I не могут иметь один K — похоже на копирование значения.

B8. Удельная активность считается «на 1 кг» у не вводивших массу. SampleInfoData.cs:121,124: weight = 1.0, volume = 1.0 — «не введено» неотличимо от «ровно 1». Комментарий MeasurementResultManager.cs:75-76 «Weight defaults to 0 — guard the denominator» не соответствует фактическому дефолту, гард не срабатывает. Оговорка: полное решение требует nullable-семантики полей (правка формата); в Волне 0 закрывается сообщением вместо тихого счёта.

C. Доза

C9. Теоретический путь падения при нелинейной калибровке — не достижим через текущий UI и поставку. DoseRateManager.cs:32 — безусловный каст (PolynomialEnergyCalibration); NonlinearEnergyCalibration — сестринский класс (оба от EnergyCalibration), формально допустим при десериализации (DeviceConfigInfo.cs:246, [XmlElement(typeof(NonlinearEnergyCalibration))]). Но во всём дереве единственное место, создающее его экземпляр — собственный Clone() класса (NonlinearEnergyCalibration.cs:39), остальные методы, включая конструктор расчёта, бросают NotImplementedException; в поставочных конфигах элемент NonlinearEnergyCalibration не встречается ни разу. Путь к InvalidCastException в DoseRateManager.cs:32 существует в коде, но чтобы на него попасть, в системе уже должен быть экземпляр NonlinearEnergyCalibration, а штатного способа его создать нет — риск, а не наблюдаемый сегодня дефект.

C10. Показание дозы зависит от режима отображения графика. MainForm.cs:639-641 передаёт BackgroundMode из вида спектра; DoseRateManager.cs:23-31 при Substract и наличии фона вычитает его, иначе считает по сырому. Переключение галки отображения меняет цифру дозы. Отдельно: при Substract без загруженного фона расчёт молча идёт по сырому спектру — индикатор режима и факт расходятся.

C11. Двойной учёт граничного канала. Калибровка DeviceConfigForm.cs:2550 — j < toChannel; применение DoseRateManager.cs:58 — i <= endch, при UpperBound[i] == LowerBound[i+1] канал стыка учитывается дважды.

D. Отрисовка и служебное

D12. Одна плохая область гасит отрисовку всех последующих. EnergySpectrumView.cs:2879 ShowROIBorderLine, обработка :2906-2909: catch (OutofChannelException) { break; } — цикл по областям прерывается (при этом верхняя граница в соседней ветке клампится, асимметрия). Атрибуция: найден и описан автором в arch-документе («break → continue надо сделать независимо»); здесь проверен по коду и включён в общий реестр.

D13. Масштаб маркеров строится по всем областям. EnergySpectrumView.cs:2812: условие roidefinitionData.Intencity < 100.0 || roidefinitionData.Intencity > 0.0 — дизъюнкция истинна при любом значении, фильтр не фильтрует.

D14. Фоновый спектр разделяется между экземплярами. ResultData.cs:351-352 — копирование по ссылке (this.energySpectrum = old.EnergySpectrum, this.backgroundEnergySpectrum = old.BackgroundEnergySpectrum), тогда как парный конструктор :386-387 делает глубокую копию обоих.

D15. Исключение при удалённом конфиге EasyControl. MainForm.cs:2670, :2680 — прямая индексация словаря без проверки ключа: KeyNotFoundException, если конфиг, на который ссылается EasyControl, удалён.

Как проверять

В проекте уже есть корпус tools/LibraryFitLab (69 спектров, 23 группы детекторов) с прогонщиком LibraryFitLab/Program.cs, но он тестирует только тракт идентификации и подгонки пиков (LibraryPeakFitter) — расчёт активности, доза и SampleInfoData в него не входят вовсе. Он годится как есть только для дефектов, задевающих идентификацию (косвенно A1). Для B4–B8, C9–C11 числовая приёмка (прогон «до/после» с эталонными значениями) потребует либо расширения этого харнесса до конца тракта (документ → расчёт → дозу), либо отдельного скрипта поверх MeasurementResultManager/DoseRateManager; сегодня такого инструмента в проекте нет. D12–D15 — визуальные/эксплуатационные, проверяются вручную.
